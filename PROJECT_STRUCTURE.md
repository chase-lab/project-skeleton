# Project structure guide

## Why this structure

Most reproducibility problems are boring: a script that only runs on one laptop, data nobody can find again, a package update that silently changes a result, a figure nobody can regenerate. The fixes are small habits, not a big system. This skeleton bundles those habits so you can adopt them in ten minutes instead of designing them yourself:

- one flat layout, so everyone knows where things are;
- a curated `.gitignore`, so git tracks code and not data or clutter;
- renv, so your package versions are written down;
- checkmate and testthat, so your expectations about the data are written down too;
- pins, for data that cannot or should not live in the repo.

Take what helps and delete the rest. Each piece works alone.

## The folder structure

```
.
├── README.Rmd / README.md   short overview (knit the .Rmd, commit both)
├── PROJECT_STRUCTURE.md     this guide
├── CITATION.cff, LICENSE    placeholders to fill in
├── .gitignore, .Rprofile, .here
├── data/
│   ├── raw/                 data as received            (ignored, README tracked)
│   └── processed/           data made by scripts        (ignored, README tracked)
├── R/                       reusable functions          (tracked)
├── scripts/                 numbered pipeline scripts   (tracked)
├── outputs/                 figures and tables          (ignored, README tracked)
├── tests/testthat/          data and function tests     (tracked)
└── docs/img/                logos and images            (tracked)
```

Every folder has a short `README.md` saying what goes in it. Empty folders are kept in git through that README. The tree in `README.md` is generated by `fs::dir_tree()` in `README.Rmd`, so it never goes stale. Tree choice: `fs::dir_tree()` is used because the CRAN alternatives that annotate folders (for example directotree, printtree) are interactive or niche, and the folder READMEs already carry the annotations.

## What to track and what to ignore

| Tracked (in git) | Ignored (not in git) |
|---|---|
| Code: `R/`, `scripts/`, `tests/` | Raw and large data: `data/raw/`, `data/processed/` |
| `renv.lock`, `renv/activate.R` | Outputs: `outputs/` (regenerated by scripts) |
| Templates and READMEs | Session files: `.Rproj.user`, `.Rhistory`, `.RData` |
| Small reference data you whitelist | Secrets: `.Renviron`, `*.key` |
| `CITATION.cff`, `LICENSE` | OS files: `.DS_Store`, `Thumbs.db` |

When in doubt: track what a colleague needs to rebuild everything else, ignore what the code can regenerate or what must stay private. If a file is both big and irreplaceable, it does not belong in git; see the pins section.

## .gitignore versus .git/info/exclude

| | `.gitignore` | `.git/info/exclude` | Global ignore (`core.excludesFile`) |
|---|---|---|---|
| Scope | This repository | This repository, this clone | All repositories on your machine |
| Shared via git? | Yes (tracked file) | No (inside `.git/`) | No |
| Who edits | The team, via commits | You alone | You alone |
| Typical use | Project rules: data, outputs, session files | Personal scratch files, local notes | Editor and OS files such as `.DS_Store` |

Set a global file once with `git config --global core.excludesFile ~/.gitignore_global`.

Do not use `git update-index --assume-unchanged` to hide files. It is a performance hint, not an ignore mechanism: git may silently drop the flag, it hides real changes, and it breaks on pull or checkout. Use `.git/info/exclude` instead.

Find out why a file is (not) ignored:

```bash
git check-ignore -v data/raw/my_data.csv
```

The output names the file and line of the matching rule. Note that ignoring a file does not untrack one that is already committed; use `git rm --cached <file>` for that.

## Reproducible packages with renv

Why: R has one global library per machine and nothing records which package versions produced your results. A collaborator, a reviewer, an archive such as Zenodo, or you in a year gets different versions and possibly different results. renv gives each project its own library and writes the versions to `renv.lock`.

How, first time:

```r
install.packages("renv")
renv::init()       # creates renv/, renv.lock and activates the project library
```

Then, as you work:

```r
renv::snapshot()   # record the packages you currently use in renv.lock
renv::restore()    # on another machine: install exactly what renv.lock says
```

Commit `renv.lock` and `renv/activate.R`; renv ignores its own internals. The skeleton ships no `renv.lock` because a lockfile is machine-specific; you create yours with `renv::init()`.

Quick-and-dirty path: run `renv::init()` now, `renv::snapshot()` before every commit that adds a package, and `renv::restore()` after every clone. That alone covers most of the benefit.

## Formatting and linting with air and jarl

What: air formats R code and jarl lints R code. Both are fast standalone binaries, not R packages, so they need no R session and are not tracked by renv. Install each following its own documentation.

Why: consistent formatting gives clean diffs, fewer style debates in review, and a linter catches mistakes (unused objects, risky constructs) early. Both are optional.

```bash
air format .     # rewrite R files in place with a consistent style
jarl check .     # report lints for R files in the current folder
```

Run `air format --help` and `jarl check --help` for the other options (for example `air format --check` only reports files that would change). Running both automatically on every commit is provided by the `githooks` branch; see the next section.

## Testing your data with checkmate and testthat

Why: your analysis rests on expectations about the data (this column exists, ids are unique, temperatures are plausible). Written down, they catch problems at input, during manipulation and at output; unwritten, they fail silently.

- checkmate: fast asserts inside your functions and scripts. They stop the run immediately with a clear message.
- testthat: expectations run on demand (or in CI), reported as a test suite.

A worked example. `R/check_data.R` defines `check_dataset()`, which asserts a data frame, required columns, and a non-missing, unique id column:

```r
source(file = fs::path("R", "check_data.R"))

raw <- data.frame(id = 1:3, site = c("a", "b", "c"))
raw |>
  check_dataset(required_columns = "site", id_column = "id")
```

The same expectation as a test lives in `tests/testthat/test-data-structure.R`. Run all tests with:

```r
testthat::test_dir("tests/testthat")
```

The templates that point at your data are skipped (`testthat::skip("TEMPLATE: ...")`) so a fresh clone passes. Remove the `skip()` lines once they point at your files. As an extension, the testdat package provides ready-made column-level expectations for data frames.

## When your data lives outside the repo: pins

Why: data may be too big for git, not yours to publish, or shared between projects. pins stores data on a "board" and lets code read it by name, with versions, so the repo holds the code and the board holds the data.

```r
board <- pins::board_folder(path = "/shared/project_data", versioned = TRUE)
pins::pin_write(board = board, x = processed, name = "processed_data")
processed <- pins::pin_read(board = board, name = "processed_data")
```

A local board in your user data directory, for data only you need:

```r
board <- pins::board_local(versioned = TRUE)
pins::pin_write(board = board, x = processed, name = "processed_data")
```

With `versioned = TRUE` every write keeps the older version; list them with `pins::pin_versions()`. Documentation: <https://pins.rstudio.com>.

## Optional add-on branches

Optional extras live in separate branches of this repository, so `main` stays small. Each branch only adds files and docs on top of `main`; nothing in `main` is changed. None of them exist yet: all three are marked coming soon, and the commands below will work once a branch is published.

- `githooks` (coming soon): tracked git hooks that run on every commit, for example `air format`, `jarl check`, re-knitting the README and running the tests, activated with one `git config` line.
- `zenodo` (coming soon): steps to archive a GitHub release on Zenodo and get a DOI, building on `CITATION.cff`.
- `website` (coming soon): a Quarto website published with GitHub Pages from the same repository.

To get one (replace `<branch>` with `githooks`, `zenodo` or `website`):

```bash
git fetch origin              # download the list of branches
git switch <branch>           # look at it without touching your work
git merge origin/<branch>     # from your own branch: bring it into your work
```
