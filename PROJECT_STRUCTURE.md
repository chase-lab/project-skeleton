# Project structure guide

> This guide documents the skeleton, for your information. Read it, then **delete this file**. Describe your own project in `README.md`, not here.

## A standard structure

Most reproducibility problems are boring: a script that only runs on one laptop, data nobody can find again, a package update that silently changes a result, a figure nobody can regenerate. The fixes are small habits, not a big system. This skeleton bundles those habits so you can adopt them in five minutes instead of designing them yourself:

- one simple layout, so everyone knows where things are;
- a curated `.gitignore`, so git tracks code and not data or clutter;
- renv, so your package versions are written down;
- testthat, so your expectations about the data are written down too;
- pins, for data that cannot or should not live in the repo.

Take what helps and delete the rest. Each piece works alone.

## The folder structure

```
.
├── README.md                short overview
├── PROJECT_STRUCTURE.md     this guide
├── CITATION.cff, LICENSE    placeholders to fill in
├── project-skeleton.Rproj   RStudio project (marks the project root)
├── .gitignore, .Rprofile
├── data/
│   ├── raw/                 data as received            (ignored, README tracked)
│   └── processed/           data made by scripts        (ignored, README tracked)
├── R/                       reusable functions          (tracked)
├── scripts/                 numbered pipeline scripts   (tracked)
├── outputs/                 figures and tables          (ignored, README tracked)
├── tests/testthat/          tests of your functions     (tracked)
└── docs/img/                logos and images            (tracked)
```

Every folder has a short `README.md` saying what goes in it. Empty folders are
kept in git thanks to that README.

## What to track and what to ignore

| Tracked (in git) | Ignored (not in git) |
|---|---|
| Code: `R/`, `scripts/`, `tests/` | Raw and large data: `data/raw/`, `data/processed/` |
| `renv.lock`, `renv/activate.R` | Outputs: `outputs/` (regenerated by scripts) |
| Templates and READMEs | Session files: `.Rproj.user`, `.Rhistory`, `.RData` |
| Small reference data you whitelist | Secrets: `.Renviron`, `*.key` |
| `CITATION.cff`, `LICENSE` | OS files: `.DS_Store`, `Thumbs.db` |

When in doubt: track what a colleague needs to rebuild everything else, ignore what the code can regenerate or what must stay private. If a file is both big and irreplaceable, it does not belong in git; see the pins section.

## When your data lives outside the repo: pins

Why: data may be too big for git, not yours to publish, or shared between projects. pins stores data on a "board" and lets code read it by name, with versions, so the repo holds the code and the board holds the data.

```r
board <- pins::board_folder(path = "/shared/project_data", versioned = TRUE)
pins::pin_write(board = board, x = processed, name = "processed_data")
processed <- pins::pin_read(board = board, name = "processed_data")
```

A local board in your user data directory, for data only you need:

```r
board <- pins::board_local(versioned = TRUE)
pins::pin_write(board = board, x = processed, name = "processed_data")
```

With `versioned = TRUE` every write keeps the older version; list them with `pins::pin_versions()`. Documentation: <https://pins.rstudio.com>.

## Reproducible packages with renv

Why: R has one global library per machine and nothing records which package versions produced your results. A collaborator, a reviewer, an archive such as Zenodo, or you in a year gets different versions and possibly different results. renv gives each project its own library and writes the versions to `renv.lock`.

How, first time:

```r
install.packages("renv")
renv::init()       # creates renv/, renv.lock and activates the project library
```

Then, as you work:

```r
renv::snapshot()   # record the packages you currently use in renv.lock
renv::restore()    # on another machine: install exactly what renv.lock says
```

Commit `renv.lock` and `renv/activate.R`; renv ignores its own internals. The skeleton ships no `renv.lock` because a lockfile is machine-specific; you create yours with `renv::init()`.

Quick-and-dirty path: run `renv::init()` just before sharing the code when
publishing the article. That alone covers most of the benefit.

Reviving an old project that has no `renv.lock`: if you remember roughly when it last worked, ask for the packages as they were on that day. renv takes them from a dated snapshot of CRAN kept by Posit Package Manager:

```r
renv::init(bare = TRUE)                      # an empty project library
renv::checkout(
  date = "2023-02-08",                       # the day it last worked
  actions = c("snapshot", "restore")         # install them and write renv.lock
)
```

By default `checkout()` covers every package your scripts use. Mind the R version too: the packages of 2023 were built for the R of 2023. Details: <https://rstudio.github.io/renv/reference/checkout.html>.

## Testing your data with testthat

Why: your analysis rests on expectations about the data (this column exists, ids are unique, temperatures are plausible). Written down, they catch problems at input, during manipulation and at output; unwritten, they fail silently.

One tool, two places:

- In your scripts (`scripts/`), testthat's `expect_*()` functions check your **data** every time the script runs. Outside a test file, a failed expectation simply stops the run with a clear message. Check at the door (input), after every join or reshaping step, and on the way out (output).
- In `tests/testthat/`, testthat tests your **functions** in `R/`, when you ask for it. It tells you that the helpers you wrote still do what you think they do.

`scripts/2_wrangle.R` shows the pattern. `R/check_data.R` defines `check_dataset()`, which expects a data frame, the required columns, and a non-missing, unique id column:

```r
source(file = fs::path("R", "check_data.R"))

raw <- data.frame(id = 1:3, site = c("a", "b", "c"))
raw |>
  check_dataset(required_columns = "site", id_column = "id")
```

Joins deserve the most care, because a wrong join corrupts a result without any error. Be explicit and intentional about what a join may do, with `relationship` and `unmatched`:

```r
library(dplyr)

processed <- left_join(
  x = raw,
  y = sites,
  by = join_by(site_id),
  relationship = "many-to-one", # a duplicated site would multiply rows: stop
  unmatched = "drop"            # sites that no row uses: drop on purpose
)

# a row without a site gets NA: stop
testthat::expect_false(object = anyNA(processed[["region"]]))
```

Writing these arguments makes you think about the join, and it saves you from writing a separate test for it.

Reshaping works the same way. Left to its defaults, `tidyr::pivot_wider()` turns duplicated rows into list-columns (with only a warning) and leaves gaps as `NA`. Say what you want instead, and check the result:

```r
wide <- tidyr::pivot_wider(
  data = counts,
  id_cols = site_id,           # which columns identify a row: not "all the others"
  names_from = species,
  names_prefix = "abund_",
  values_from = abundance,
  values_fn = sum,             # duplicated site and species: add them up, on purpose
  values_fill = 0              # a species not seen at a site: 0, on purpose
)

testthat::expect_equal(object = nrow(wide), expected = dplyr::n_distinct(counts[["site_id"]]))
```

`pivot_longer()` is the same: say `cols`, `names_to` and `values_drop_na` yourself.

The tests of `check_dataset()` itself live in `tests/testthat/test-check_data.R`. This project is not a package, so `devtools::test()` does not apply. Run all tests with:

```r
testthat::test_dir("tests/testthat")
```

As an extension, the testdat package provides ready-made column-level expectations for data frames.

## Formatting with air

What: air is a fast code formatter for R. It rewrites your code in one consistent style, so diffs show real changes and nobody argues about spaces. Both air and the linter jarl are standalone programs, not R packages, so renv does not track them. Install air following <https://posit-dev.github.io/air/>.

```r
# Before
1+2:3*(4/5)
# After
1 + 2:3 * (4 / 5)
```

In RStudio, tell it to use air as the external formatter: `Tools -> Global Options -> Code -> Formatting`, set `Code formatter:` to `External` and `Reformat command:` to `{path/to/air} format` (`which air` in a terminal gives the path). To format on every save, tick `Reformat documents on save` under `Tools -> Global Options -> Code -> Saving`.

Running air and jarl (a linter that catches likely mistakes) automatically on every commit is provided by the `githooks` branch; see the next section.

## Optional add-ons

Optional extras live in separate branches of this repository, so `main` stays simple.

- `zenodo`: steps to archive a GitHub release on Zenodo and get a DOI, building on `CITATION.cff`.
- `website`: a Quarto website published with GitHub Pages from the same repository.
- `githooks`: tracked git hooks that run on every commit, for example `air format`, `jarl check` and running the tests, activated with one `git config` line (see "Git hooks" above).

Each branch has its own README explaining what it adds and how to use it. Browse them on GitHub: [`zenodo`](https://github.com/chase-lab/project-skeleton/tree/zenodo), [`website`](https://github.com/chase-lab/project-skeleton/tree/website), [`githooks`](https://github.com/chase-lab/project-skeleton/tree/githooks).

## Git hooks

What: a git hook is a script that git runs automatically at a given moment, for example just before a commit is created. Used well, hooks stop badly formatted code, likely mistakes and failing tests before they enter the history.

Why they are normally untracked: hooks live in `.git/hooks`, and git never tracks the `.git` folder. So you cannot share hooks through the repository, and every colleague would have to copy them by hand.

How the `githooks` branch works: the hooks are ordinary files in a tracked folder, `.githooks/`. One line tells git to use that folder instead of `.git/hooks`. Each person runs it once per clone:

```sh
git config core.hooksPath .githooks
```

- `pre-commit` runs `air format --check` and `jarl check` on the staged R files, then the tests (`Rscript tests/testthat.R`).
- `pre-push` runs the tests only.
- air is a formatter: it rewrites code in one consistent style. The hook only checks; if it fails, run `air format .` and commit again.
- jarl is a linter: it points at likely mistakes, such as `T` instead of `TRUE`, without changing your code.
- If air or jarl is not installed, the hook warns, gives the install link and skips that check. It never blocks you for a missing tool.
- To skip the hooks once: `git commit --no-verify` (or `git push --no-verify`).

Both tools are installed as described in the section above and in the `.githooks/README.md` of the branch.
